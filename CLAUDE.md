Contexte pour Claude Code (et toute IA assistante) travaillant sur ce dépôt.

## Le projet

`mercure_crm` est un CRM WhatsApp interne pour **RETAIL GROUP**, une entreprise de prêt-à-porter contemporain basée à Libreville (Gabon), positionnée moyen-haut de gamme (pas de la haute couture). Le groupe exploite 4 enseignes, chacune avec son propre numéro WhatsApp Business à terme :

| Boutique | Segment |
|---|---|
| **Adidas** | Sport, sneakers, streetwear |
| **Carré** | Prêt-à-porter masculin |
| **Mango** | Mode féminine contemporaine |
| **Grand Store** | Grand magasin généraliste multi-marques |

Chaque boutique gère aujourd'hui WhatsApp de façon artisanale (téléphone personnel, pas de fiche client unifiée, campagnes envoyées sans segmentation ni consentement documenté). L'objectif du projet est de centraliser cette relation client : connexion officielle à l'API WhatsApp Cloud, boîte de réception partagée par boutique, chatbot de qualification, segmentation et score RFM des clients, campagnes ciblées, automatisations.

**Spécification complète** : [`docs/Cahier des charges - CRM WhatsApp Retail Group.docx`](docs/Cahier%20des%20charges%20-%20CRM%20WhatsApp%20Retail%20Group.docx) — analyse fonctionnelle, périmètre par module (connexion WhatsApp, chat, chatbot, gestion des contacts, segmentation RFM, campagnes, automatisations, analytics), architecture, modèle de données, MVP détaillé. Se référer à ce document avant d'ajouter une fonctionnalité non listée ici.

## Stack technique

- Backend : Laravel 13 (PHP ^8.3)
- Frontend : React 19 + TypeScript, via Inertia.js 3
- Build : Vite 8 + `laravel-vite-plugin`
- UI : Tailwind CSS 4
- Tests : Pest 4 (+ `pest-plugin-laravel`)
- Style de code : Laravel Pint
- Queue : Laravel Queue (driver `database`) — tout appel à l'API WhatsApp déclenché par une action utilisateur (campagne) doit passer par un Job, jamais un appel synchrone dans le contrôleur HTTP
- API externe : **WhatsApp Business Platform / Cloud API officielle (Meta Graph API) uniquement** — jamais de connexion non officielle par QR code ou session WhatsApp Web (décision produit actée dans le cahier des charges)

php artisan key:generate

## MVP en cours

Périmètre (cahier des charges §7, élargi au parcours client le 30/09/2026) :
1. Connexion à l'API WhatsApp par boutique (formulaire admin, test de connexion).
2. Import de contacts par boutique (CSV/Excel, mapping, normalisation E.164, détection de doublons).
3. Envoi de campagne à une liste de contacts importés (template Meta approuvé, envoi par lot en file d'attente).
4. **Fiche client unique et parcours client** : une fiche par personne pour tout le Groupe, étape calculée automatiquement (Contact → Prospect → Nouveau client → Client actif → À risque → Inactif) et **statut VIP par boutique** (top X % des acheteurs de chaque boutique : un client peut être VIP chez Mango et pas chez Adidas), seuils modifiables par organisation, historique des changements d'étape, ciblage des campagnes par étape, entonnoir dans le tableau de bord.
5. **Multi-entreprise (MVP du 17/10/2026)** : inscription d'une entreprise (`/register`) ; Paramètres → WhatsApp par établissement (identifiants chiffrés, test chez Meta, enregistrement du numéro) ; webhook par établissement (`/webhooks/whatsapp/{clé}`, signature X-Hub-Signature-256 avec l'App Secret, traitement en file, idempotence par wamid) ; statuts remis/lu/échec des messages de campagne et réponse « Stop » qui retire l'opt-in. Le compte Meta partagé du `.env` n'est un repli que pour les organisations historiques (`organizations.uses_shared_whatsapp_account`).

6. **MVP Menentia sans API WhatsApp (19/10/2026)** : la vérification Meta étant bloquée (numéros Airtel), le CRM doit fonctionner sans l'API. Segmentation RFM, score client 0-100 et risque de churn enregistrés sur chaque fiche (`App\Services\CustomerScoring`, recalculés chaque nuit et après un import d'achats) ; rendez-vous par établissement (`appointments`, agenda `/appointments`, fiche client) ; **Actions du jour** (`/actions`, `App\Services\ActionLists`) : listes de clients à relancer avec lien `wa.me` et message prérempli modifiable par l'entreprise, envoi manuel depuis le téléphone de l'établissement, relance tracée (`customer_follow_ups`). L'API WhatsApp est optionnelle par entreprise (`organizations.whatsapp_api_enabled`, Organisation → « Envoi automatique par l'API WhatsApp ») : désactivée, campagnes, modèles, historique des messages et Paramètres WhatsApp sont masqués et leurs routes protégées par le middleware `whatsapp-api`. Une nouvelle inscription démarre sans API ; les organisations existantes la gardent. Positionnement : CRM pour les entreprises sur rendez-vous en Afrique francophone, marque Menentia.
7. **Prestations et produits (20/10/2026)** : un seul catalogue (`catalog_items`, type `service` = prestation avec durée, réservable ; `product` = produit vendu, sans réservation ni stock), Paramètres › Catalogue. Un rendez-vous reprend ses prestations (`appointment_items`, prix et durée copiés au moment du choix) ; « Encaisser » crée la vente à lignes (`purchase_items`) et passe le rendez-vous à « Honoré ». Les ventes importées sans ligne restent valables. Tableau de bord : CA prestations / produits, top prestations, panier moyen par visite.
8. **Réservation en ligne (20/10/2026)** : page publique `/rdv/{slug}` sans compte (prestations réservables, créneau libre, nom + numéro WhatsApp, consentement facultatif daté), confirmation avec lien d'annulation (`appointments.cancel_token`) et récapitulatif wa.me vers le numéro de l'établissement. Créneaux calculés par `App\Services\BookingAvailability` (horaires et capacité par établissement, pas, délai minimum, horizon) ; la vérification et l'enregistrement se font dans une transaction qui verrouille l'établissement (deux demandes pour le dernier créneau : la seconde reçoit « créneau pris »). Réservation « À confirmer » (statut `requested`) par défaut, confirmation automatique possible ; réglages dans Paramètres › Réservation en ligne (`organizations.booking_settings`). Quotas `booking-slots` / `booking-submit` (AppServiceProvider).
9. **Cahier de cadrage du 28/10/2026** (référence : `/mnt/project-files/cadrage/menentia-cahier-de-cadrage-final-2026-10-28.pdf`) : interface bleu-vert (bleu #0E7BD6, vert #00C896, bleu nuit #0B2D4A, fond #F4F8FB ; petit texte #0A66B2 / #007A5C), logo M en dégradé sans point. Agenda : pause quotidienne (`stores.booking_break`), fermetures (`closures` : fériés, congés, pour un établissement ou toute l'entreprise), intervenants (`staff_members` : horaires propres ou ceux de l'établissement, prestations, réservables en ligne ; `appointments.staff_member_id`) ; en ligne, le client choisit son intervenant ou « peu importe » (le moins chargé). Rapport quotidien au dirigeant (`App\Services\DailyReport`, vue `reports/daily`, `crm:daily-report` toutes les 15 min, Paramètres › Rapports ; PDF joint si `barryvdh/laravel-dompdf` est installé) ; moyen de paiement à l'encaissement (`purchases.payment_method`). Fidélité (`App\Services\Loyalty`, `loyalty_transactions`, `loyalty_rewards`, `organizations.loyalty_settings`) : points par FCFA à chaque achat à partir de la date de lancement, paliers sur 12 mois, récompenses échangées depuis la fiche.

10. **Demandes de démo du site vitrine (29/10/2026)** : `POST /api/public/v1/leads` (`routes/api.php`, `Api\LeadController`, table `leads`, sans lien avec une organisation : ce sont les prospects de Menentia). Le formulaire statique de menentia.com/contact poste directement ici ; réponse : redirection vers `MENENTIA_SITE_URL/contact#merci`, ou 201 en JSON. Champ caché `site_web` anti-robots, quota `leads` (5/min par IP), email à `MENENTIA_LEADS_EMAIL` après la réponse si renseigné.

11. **Secteur d'activité et analyse par familles (29/10/2026)** : à l'inscription, l'entreprise choisit son secteur (`organizations.sector`, liste et descriptions dans `Organization::SECTORS` : beaute, sante, sport, technique, pro, commerce, autre ; modifiable dans Organisation ; null = organisation historique, tout affiché). Le commerce n'a ni agenda (menu Agenda, Réservation en ligne, Intervenants, Fermetures masqués) ni catalogue à gérer : il analyse ses ventes au **niveau choisi par l'entreprise** (`organizations.product_analysis_level` : article, famille ou catégorie, cf. section Menentia Retail) ; les familles sont la table `categories` (appelées « catégories » dans les autres secteurs), une catégorie étant une famille parente (`categories.parent_id`). Ciblage dans Fiches clients (donc groupes et campagnes) : `family` + `family_mode` (bought / lapsed) + `family_days`, `family_not` (jamais acheté), `prop` (« genre:Femme »).

Socle toujours actif (clients, ventes, analyses, actions du jour, rapport du soir) ; un module décoché disparaît du menu, des fiches et des réglages. Modules : `rdv`, `seances_groupe` (`group_classes`, `class_sessions` dates en texte, `class_enrollments`, `attendances`, `App\Services\GroupClasses`), `abonnements` (`plans`, `subscriptions`, `App\Services\Subscriptions`), `tranches` (`payment_schedules`, `installments`, `App\Services\Installments` : une tranche encaissée = une vente), `beneficiaires` (`customers.responsible_id`, numéro facultatif, note de santé chiffrée ; messages au responsable via `Customer::recipient()`), `lieux`, `catalogue`, `familles`, `fidelite`, `campagnes` (= `whatsapp_api_enabled`). Tout revient à la fiche client (onglets de modules), aux Actions du jour, au ciblage (`follow` dans `CustomerSearch`), à l'alerte de départ et au rapport du soir. Libre-service : « Pour bien démarrer » (`App\Services\Onboarding`), modèles Excel `/modeles/{kind}`, import des personnes suivies, lien « Besoin d'aide ? » (`MENENTIA_SUPPORT_WHATSAPP`). Démo : `php artisan demo:sport`, guide `docs/demo-sport.md`.

Remises : `purchases.loyalty_discount_percent` (colonne `remise_fidelite` de l'import) et `loyalty_redemptions` (bouton de la fiche). Ne pas anticiper ces fonctionnalités dans le code tant qu'elles ne sont pas explicitement demandées.

## Menentia Retail

Une seule application, deux offres : **Menentia** (PME sur rendez-vous) et **Menentia Retail** (`organizations.sector = 'commerce'` : chaînes de boutiques, de restaurants, distributeurs de produits de grande consommation dont les clients sont des grossistes ou revendeurs). Vocabulaire générique (vente, ticket ou facture, article, famille, point de vente, marque/enseigne) : aucun terme propre à un métier dans l'UI. Les deux offres peuvent être multi-marques et multi-points de vente ; tout reste centré sur le **client**. Ni catalogue, ni stock, ni variantes, ni IA ou prédictif. Cible MySQL, tests sur SQLite (SQL portable : `substr` pour les dates, pas de fonctions propres à un moteur).

- **Fondations** : `organizations.currency` (XAF), `timezone` (Africa/Libreville), `product_analysis_level` (product | family | category), `rfm_settings` ; `stores.code` (code caisse, sert à reconnaître le point de vente à l'import), `city`, `is_active` ; `roles.can_import`, `can_export` (`User::canImport()`, `canExport()`) et rôles types Retail (`Role::retailDefinitions()` : Admin groupe, Direction, Resp. marque, Resp. boutique, Marketing, Opérateur d'import, créés pour le commerce, ajoutables via `/roles/presets`). Journal d'audit `audit_logs` via `App\Services\Audit` (imports, exports, fusions, corrections de vente, marques, points de vente, utilisateurs, paramètres), écran Paramètres › Journal.
- **Tickets** : `purchases` est la table des tickets (1 achat = 1 ticket) et `purchase_items` leurs lignes ; encaissement d'un rendez-vous, fidélité, parcours client, RFM, familles et rapport du soir lisent la même source. Colonnes : `receipt_number`, `source_key` (unique par point de vente : idempotence), `type` sale | return (retour = montants négatifs, `original_purchase_id`), `status` valid | cancelled (scope global `valid` sur `Purchase` ; `Purchase::withCancelled()` pour les voir ; toute requête `DB::table('purchases')` doit filtrer `status = valid`), `discount_amount`, `subtotal`, `currency`, `import_batch_id`, `customer_code`, `buyer_name`. `contact_id` facultatif = **vente anonyme**, gardée dans le CA sans créer de client. Agrégats client : `Purchase::SQL_SALES_COUNT`, `SQL_FIRST_SALE`, `SQL_LAST_SALE` (un retour réduit le CA sans compter comme achat). Annulation d'un ticket : motif obligatoire, journalisée, jamais de suppression silencieuse. Écran Ventes : filtres tickets / retours / annulés / anonymes / import, détail `/purchases/{id}`, export CSV (droit d'export, périmètre, journalisé).
- **Import des ventes v2** (`App\Services\SalesImport`, `ProcessSalesImportJob`, `/sales-imports`) : dépôt (stockage privé, empreinte sha256 : un fichier déjà importé est refusé tant que son lot n'est pas annulé) → association des colonnes (reconnue automatiquement, modèles `import_mappings`) → vérification ligne par ligne (`import_rows` : valid / rejected avec code et message par n° de ligne / duplicate d'un ticket déjà importé) → rapport d'erreurs CSV / XLSX → confirmation → traitement en file par paquets et transactions → bilan. Obligatoires : date, point de vente (colonne nom ou code, ou fixé au dépôt), montant (ou quantité × prix) et **famille ou catégorie** (colonne, ou famille par défaut choisie au mapping, utile aux tickets de totaux des restaurants) ; une famille inconnue n'est pas une erreur, elle part dans « À classer ». Sans n° de ticket : un ticket par client, jour et point de vente. Colonnes libres = attributs. Clients entreprises (`customers.type` person | business, `company_name`, `contact_name`) et code client de la caisse (`customers.external_code`, rapproche une facture sans téléphone). Annuler un lot supprime ses ventes proprement (fidélité, fiches) et se journalise. L'import d'achats historique (`PurchaseImporter`) reste en place pour les autres secteurs.
- **Référentiel client** : `customer_phones` (principal, anciens numéros datés, `is_shared`), `customer_consents` (canal, finalité, point de vente ; tenu à jour depuis `contacts.consent_status`, qui reste la référence des envois), `customer_match_reviews` : un numéro connu avec un nom très différent (`CustomerIdentity::namesMatch`) ou un numéro partagé n'est **jamais rattaché d'office** : la vente reste non rattachée et part dans Clients › À vérifier (rattacher / autre personne). Fusion et séparation de fiches (`CustomerIdentity::merge()` / `split()`), journalisées. Limite connue : un même numéro ne peut pas porter deux fiches (unicité organisation + numéro) ; « autre personne » garde donc la vente non rattachée avec le nom lu.
- **Analyses** (`App\Services\RetailAnalytics`, `/analytics/{direction|network|families|clientele|retention|quality}`, `/multibrand`) : filtres communs période / marque / point de vente / famille (sous-familles comprises), bornés par le périmètre du rôle ; CA net = ventes − retours − remises ; export CSV / Excel de chaque tableau et rapport de direction imprimable (`/analytics/report`, PDF si dompdf), journalisés. Le niveau d'analyse paramètre `FamilyAnalytics` (rapport du soir, onglet Familles) et le ciblage (`family` d'une catégorie = toutes ses familles ; `article`).
- **Multimarque et RFM v2** : `customer_brand_metrics` (premier / dernier achat, tickets, CA net et RFM du client dans chaque marque, `App\Services\BrandMetrics`, recalculé après import, annulation, fusion via `RefreshBrandMetricsJob` et chaque nuit par `crm:refresh-lifecycle`), `customers.brands_count`, règles RFM paramétrables et versionnées (`Organization::RFM_DEFAULTS`, Paramètres › Segments RFM ; les 8 segments historiques par défaut), historique `customer_segment_history`. Fiches clients : `brands` (multi / mono), `segment` dans la marque choisie, `never_brand` (vente croisée) — donc aussi groupes, audience et campagnes. Actions du jour : liste `cross_sell` (fidèles d'une marque jamais venus dans une autre, variable `{autre_marque}`), filtre par marque.
- **Démonstration** : `php artisan demo:retail` (cf. Commandes) ; fichiers Excel d'exemple dans `docs/exemples/`, captures dans `docs/apercu-retail/`.

## Décisions d'architecture à respecter

- **Multi-boutique dès la conception.** Toute donnée métier (contact, conversation, campagne) est rattachée à une boutique (`store_id`), même quand le MVP n'affiche qu'une vue simple.
- **Jamais de secret en dur dans le code.** Les identifiants WhatsApp (token, `phone_number_id`) se lisent via `config('services.meta_whatsapp.*')` (donc `.env`), jamais codés en dur ni committés. Historique du projet : un access token Meta a déjà fuité dans d'anciens scripts PHP autonomes conservés à titre de référence dans `whatsapp_service/` (`test.php`, `whatsapp.php`, `whatsapp_single.php`) — **ne jamais reproduire ce pattern**, et ne jamais committer de nouveau token en clair.
- **Le module WhatsApp est un service applicatif, pas un script.** Toute la logique d'appel à l'API Graph passe par `App\Services\WhatsAppClient` (basé sur `Illuminate\Support\Facades\Http`, donc Guzzle) et son exception dédiée `App\Services\WhatsAppApiException`. Les scripts de `whatsapp_service/` sont des prototypes de référence, pas du code destiné à s'exécuter en production.
- **Envoi de messages toujours asynchrone.** Tout envoi de campagne doit passer par un Job Laravel en file d'attente (jamais un appel direct dans le contrôleur HTTP), pour ne jamais bloquer une requête sur un appel réseau externe.
- **Consentement WhatsApp obligatoire avant toute campagne marketing.** Un contact sans statut `opt-in` documenté ne doit jamais recevoir de template de catégorie Marketing.
- **Fiche client unique (`customers`) + contacts par boutique.** Une personne = une fiche par organisation et numéro E.164 ; chaque `contact` reste sa relation avec une boutique (consentement propre au numéro WhatsApp de la boutique, statut VIP de la boutique `is_vip`, bienvenue, groupes) et porte `customer_id`. Le rattachement, les compteurs d'achats et l'étape sont gérés uniquement par `App\Services\CustomerLifecycle` (déclenché par les événements des modèles `Contact` et `Purchase`, regroupé en fin d'import avec `CustomerLifecycle::batch()`). Le nom du contact le plus récent l'emporte sauf identité confirmée à la main ; un changement de numéro conserve l'ancien dans `previous_phones`. L'étape n'est jamais saisie à la main.
- **Tâche planifiée.** `crm:refresh-lifecycle` tourne chaque nuit (`routes/console.php`) car les passages « À risque » / « Inactif » dépendent du temps : le serveur doit exécuter `php artisan schedule:run` chaque minute (cron cPanel).

## Déploiement

**Hébergement cible : Azure App Service** (workflow à écrire). En attendant, le déploiement automatique est désactivé : `.github/workflows/deploy.yml` (SSH/cPanel) ne se lance plus qu'à la main (`workflow_dispatch`). Ancien déploiement via SSH/cPanel, sur le même serveur qu'un projet précédent — le workflow est réutilisé et adapté pour ce projet. Le secret GitHub `DEPLOY_PATH` doit pointer vers le répertoire dédié à **mercure_crm** sur ce serveur ; vérifier/mettre à jour ce secret (ainsi que `SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY`, `SSH_PASSPHRASE`, `SSH_PORT`) dans les paramètres du dépôt GitHub avant le premier déploiement.

Tâche cron à créer une fois dans cPanel (sinon les étapes du parcours client ne vieillissent pas) : `* * * * * cd <DEPLOY_PATH> && php artisan schedule:run >> /dev/null 2>&1`. Le déploiement lance aussi `crm:refresh-lifecycle` après la migration.

Règle absolue, quel que soit le projet : ne jamais utiliser `migrate:fresh` ou `migrate:refresh` en déploiement — uniquement `migrate --force`, pour ne jamais perdre de données clients, de conversations ou de campagnes en production.

## CI

- `.github/workflows/tests.yml` : exécute le style de code (Pint) puis les tests (Pest) sur chaque push/PR vers `staging`/`main`. Réutilisable via `workflow_call`.
- `.github/workflows/deploy.yml` : lancement manuel uniquement (en attente du workflow Azure App Service) ; rejoue `tests.yml` puis déploie en SSH/cPanel.
